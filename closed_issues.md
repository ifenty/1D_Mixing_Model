## RESOLVED: KPP Python port's forcing-validation gate failed systemically on `global_oce_latlon`'s realistic multi-column configuration — two independent root causes found, one fixed at the capture level, one downgraded from data-destroying to diagnostic-only

**Date Identified**: 2026-09-19T12:30:00Z
**Date Resolved**: 2026-09-19T13:45:00Z
**Status**: Resolved
**UUID**: 1DMIX-022
**Anchors**: `mitgcm_verification_mods/kpp_mods/kpp_calc.F` (`INPUT_FORCING` dump); `Vertical_Mixing_Models/KPP/kpp_core_driver.py::_validate_forcing_computation`

### Issue
`_validate_forcing_computation` raised a hard `ValueError` whenever Python's independently-recomputed `ustar`/`bo`/`bosol` differed from MITgcm's captured values by more than 1%; the caller's broad `except Exception` turned that into a dropped column, leaving its entire output (all levels, `hbl` included) at the NaN pre-fill. For the 3 previously-tested experiments this 1% gate was essentially never tripped. For `global_oce_latlon` (real bathymetry, spherical-polar grid, `useCDscheme`, `useGMRedi`, periodic climatological forcing — none exercised by the prior 3), the gate failed for ~99.5% of wet columns: of 9260 wet column-timesteps, only ~50 produced usable output.

### Resolution and justification
Found two independent, real root causes, both with direct Fortran citations:

1. **`tau_x`/`tau_y` capture didn't match the grid point KPP actually uses them at.** `kpp_forcing_surf.F:191-208` computes `ustar` from `surfForcU(i,j,bi,bj) + surfForcU(i+1,j,bi,bj)` (and the V equivalent) — i.e. it *averages the two neighboring U/V-grid-edge points onto the T-grid center* before computing `ustar = sqrt(sqrt((Usum)²+(Vsum)²)*0.5)`, since `surfaceForcingU`/`V` live on the staggered C-grid edge, not the T-grid center where KPP diagnoses `ustar`/`hbl`. `kpp_calc.F`'s `INPUT_FORCING` dump instead captured the single raw edge value `surfaceForcingU(i,j,bi,bj)` verbatim. For a spatially near-uniform wind field (all 3 prior experiments), adjacent-point averaging ≈ the single-point value, so this was invisible; for `global_oce_latlon`'s realistic, spatially-varying Trenberth climatology, it produced systematic `ustar` errors up to ~7%. Algebraically verified `ustar_python = ((Usum/2)² + (Vsum/2)²)^0.25` is *exactly* MITgcm's `sqrt(sqrt(work3)*0.5)` (with `work3=(Usum)²+(Vsum)²`) — confirmed directly on the real capture: replacing the single-point tau with the two-point average dropped the median wet-column `ustar` relative error from 2.68% to exactly 0.0%, and the fraction of wet columns exceeding 1% relative error from 75.7% to 8.4%. Fixed `kpp_calc.F`'s dump to capture `0.5*(surfaceForcingU(i,j,bi,bj)+surfaceForcingU(i+1,j,bi,bj))` (and the V equivalent) instead of the raw single-edge value.

2. **Raw-flux capture omits MITgcm's surface climatological restoring term.** `external_forcing_surf.F:172-176` calls `FORCING_SURF_RELAX` (active whenever `doThetaClimRelax`/`doSaltClimRelax`, which `global_oce_latlon`'s `tauThetaClimRelax`/`tauSaltClimRelax` namelist settings enable) *before* adding the `Qnet`-derived contribution into `surfaceForcingT` (line 226: `surfaceForcingT = surfaceForcingT - (Qnet...)`, i.e. additive onto whatever the restoring call already put there). `kpp_calc.F`'s raw `Qnet`/`Qsw`/`EmPmR`/`saltFlux` dump captures only the flux-input piece, never the separately-added restoring contribution — a real, sourced gap in the raw-flux-reproduction pipeline for any experiment using climatological surface restoring (none of the prior 3 do). This explains the residual, still-real `bo` mismatches (up to 25% relative error, though `bo` itself is ~1e-8, so the absolute gap is tiny) that remained after fix (1) alone.

Rather than extending the raw-flux pipeline to also replicate `FORCING_SURF_RELAX` (a nontrivial undertaking, and orthogonal to what this check is actually needed for), downgraded `_validate_forcing_computation` from a hard `raise` to `warnings.warn`. This is safe because `compute_mixing`'s Mode 3 branch *always* uses `ustar_forcing`/`bo_forcing`/`bosol_forcing` (MITgcm's own captured ground truth) for the actual mixing computation regardless of this check's outcome (confirmed by reading the code directly, `kpp_core_driver.py:300-316`) — the check is a pure diagnostic on the Python-recomputation path, and previously aborted `hbl`/`visc_az`/etc. that have zero dependency on it succeeding.

### Verification and remaining bounds
Re-ran the full pipeline on `global_oce_latlon` after both fixes: `hbl` NaN count dropped from 14350/14400 (99.65%) to exactly 5140/14400 (35.7%) — matching the independently-confirmed land-column count (1285 land columns × 4 timesteps) precisely, i.e. **zero remaining wet-column data loss**. `hbl` agreement over all wet columns: median diff 0.0013 m, p95 0.023 m, p99 0.66 m, only 0.14% of wet columns exceed 5 m diff — matching or exceeding `lab_sea`'s already-accepted quality bar (median 0.0042 m, 1DMIX-019). Full pytest suite: `50 passed, 3 skipped`, confirmed after both the `kpp_calc.F` capture change and the `kpp_core_driver.py` warn-instead-of-raise change (the latter touches the shared KPP driver used by all 4 experiments; no test asserts on the raised exception). Remaining, accepted bound: `bo`'s raw-flux-reproduction validation will still show elevated relative error specifically for climatologically-restored experiments (root cause 2, not fixed at the formula level) — this is now diagnostic-only (a warning), does not affect any mixing coefficient, and is fully explained/sourced above; extending the raw-flux pipeline to include restoring terms is a distinct, lower-priority follow-up if precise `bo`-formula validation for this configuration class is wanted later.

### Traceability
No commit yet (pending owner authorization). Files changed: `MITgcm_to_Python_port_verification/mitgcm_verification_mods/kpp_mods/kpp_calc.F` (tau_x/tau_y capture), `Vertical_Mixing_Models/KPP/kpp_core_driver.py` (`_validate_forcing_computation` raise→warn).

## RESOLVED: KPP Python port's `hbl` diagnosis is sensitive to razor-thin Rib/Ricr threshold crossings — characterized as an inherent floating-point sensitivity, not a port defect

**Date Identified**: 2026-09-19T07:10:00Z
**Date Resolved**: 2026-09-19T09:15:00Z
**Status**: Resolved
**UUID**: 1DMIX-019

### Issue

Traced to its root: at one example column (lab_sea, t=1, x=19, y=4), `hbl` itself disagreed (Python 67.4 m vs. MITgcm 41.0 m) because the bulk Richardson number `Rib` at one level (`Rib[3]=0.299`) sits 0.3% below the critical threshold `Ricr=0.3` in the Python port's computation — a razor-thin miss that causes the boundary-layer search to lock onto a much deeper crossing instead.

### Resolution and justification
Verified the crossing-search algorithm is an exact match to MITgcm's real Fortran logic (`kpp_routines.F:655`, "first exceedance, lock in permanently," including never revisiting `kbl`). The remaining tiny (4th-5th significant figure) numerical differences — an unavoidable consequence of two independent floating-point implementations computing the same physics via different code paths (EOS calls, gradient formulas, etc.) — get massively amplified into a large `hbl` difference only because this specific level's `Rib` happens to sit within a fraction of a percent of the hard `Ricr` cutoff. ### Verification and remaining bounds

Full pytest suite: `50 passed, 3 skipped` throughout. Temporary Fortran instrumentation reverted (never committed); temporary Docker build/run/input directories (~120 MB) deleted after extracting results.

**Addendum (2026-09-19, 6-month `lab_sea` rerun, 655,200 wet column-timesteps, ~4.4x the original sample)**: same mechanism, confirmed at a larger and more extreme scale, not a new or different cause. Widens this issue's own quantified bound (larger tail than originally stated) but does not change its conclusion (inherent finite-precision sensitivity of a hard-thresholded diagnostic, not a port defect) — recorded here rather than as a new issue, since the mechanism and evidence are the same, just from a longer, more representative sample.

## RESOLVED: Standalone KPPMIX harness diverges from full-model MITgcm at the deepest grid levels — root cause was a silent float-parsing bug in the capture pipeline, not physics

**Date Identified**: 2026-09-16T00:00:00Z
**Date Resolved**: 2026-09-19T08:50:00Z
**Status**: Resolved
**UUID**: 1DMIX-012

### Issue
A standalone-subroutine harness (`mitgcm_verification_mods/kpp_standalone_driver/`) compiles and calls `KPPMIX` directly, fed by inputs from a real instrumented full-model run. Across 10 captured timesteps (1D_ocean_ice_column), `visc_az`/`diff_kz_s`/`diff_kz_t` diverged from the full model by a bounded but real amount (~5e-3 m²/s) at the deepest 4-5 grid levels, from timestep 1 onward. The original hypothesis ("boundary layer reaches the domain bottom") was disproven by direct measurement (`hbl≈33m`, nowhere near the 23-level domain's actual bottom); four further hypotheses (stale memory, bathymetry truncation, level-dependent viscosity, vertical Ri-smoothing) were each tested and disproven with hard evidence.

### Resolution and justification
Added temporary, throwaway debug instrumentation directly inside `kpp_calc.F` (reverted after use, never committed) dumping the exact `shsq`/`dbloc`/`Ritop` values at the point they are passed into `KPPMIX`. This revealed the raw MITgcm text output at the affected levels contains genuinely nonzero values (e.g. `dbloc≈0.001-0.003`, `Ritop≈8-17`) — completely different from the `0.0` that the parsed NetCDF showed. Root cause found in `scripts/parse_mitgcm_split.py`: Fortran's fixed-width `E`-format drops the "E" character when an exponent needs 3 digits to fit the field width (e.g. `0.105188567206-104` instead of `...E-104`), which happens for the vanishingly tiny (but physically real) `shsq` values at these genuinely quiescent deep levels. Python's `float()` cannot parse the "E"-less form and raises `ValueError`, which every call site in the parser caught via a blanket `except (ValueError, IndexError): continue` — silently dropping the *entire* line, including the otherwise-valid sibling fields `dbloc`/`Ritop`, leaving pre-initialized zeros in their place. The standalone driver, fed these wrongly-zeroed values as input, correctly (per `Ri_iwmix`'s real formula, `kpp_routines.F:1206-1208`) computes KPP's maximum-shear-instability diffusivity ceiling for a degenerate `Ri=0/0` case — mathematically confirmed by hand to reproduce the mismatched value (`viscArNr(1) + difm0 = 1.93e-5 + 0.005 = 0.0050193`) exactly. The full model, using its own correct (never mis-parsed) internal values, correctly computes background-only mixing since the real Richardson number there is not actually degenerate.

Fixed `parse_mitgcm_split.py` with a `_ffloat()` helper that also accepts Fortran's bare-exponent form, applied at all 25 `float(parts[N])` call sites. Found and fixed a second, independent bug in `scripts/export_kpp_input_for_fortran.py`: it used `!r` (repr) directly on numpy scalars without casting to `float()` first; under NumPy 2.x, `repr(np.float64(x))` includes an `np.float64(...)` wrapper that Fortran's list-directed `READ` cannot parse, causing a `Bad real number in item 1 of list input` runtime error once the first bug's fix exposed genuinely tiny values that needed export. Fixed all affected call sites to cast via `float(...)` first, matching the pattern already correctly used elsewhere in the same file. Proactively applied the identical `_ffloat()` fix to `scripts/parse_mitgcm_ggl90_split.py`, which shares the exact same vulnerable pattern (not yet observed to cause a problem there, but the same latent bug).

### Verification and remaining bounds
Re-parsed the original raw MITgcm STDOUT (`1D_ocean_ice_column/output_kppmix_extend/output.txt`, unchanged) with the fixed parser, regenerated the canonical `KPP_port_validation/{inputs,outputs}_from_mitgcm/mitgcm_kpp_{inputs,outputs}_1D_10_kppmix_extend.nc` (confirmed `Ritop`/`buoy_freq_sq` now genuinely nonzero at the previously-zeroed levels), re-exported to the standalone driver's input format, reran the standalone driver, and regenerated `outputs_from_mitgcm_standalone/mitgcm_kpp_outputs_standalone_1D_10.nc`. **Result: max diff across all 10 timesteps and all 23 levels is 1.77e-17 — floating-point roundoff, an exact match.** Full pytest suite: `50 passed, 3 skipped` (unrelated pre-existing gap), confirmed after each fix. Arch's own preliminary orientation reading (recorded in the issue's own text) traced a different, more specific candidate: MITgcm's real EOS pressure argument is **not** a flat "1 dbar ≈ 1 m." Reading `model/src/pressure_for_eos.F` (`selectP_inEOS_Zc.LE.1` branch, confirmed the active branch for `isomip` via `output.txt`'s printed `selectP_inEOS_Zc=0`), `model/src/set_ref_state.F:118-121` (no `gravityFile`, confirmed via `output.txt`'s printed `top_Pres=0`/`seaLev_Z=0`), `model/src/ini_vertical_grid.F:54` (`gravitySign=-1` for z-coordinates), and `model/inc/EOS.h:19`/`model/src/find_rho.F:507` (`SItoBar=1e-5`) together give MITgcm's real bar-per-metre-of-depth conversion factor as **`rho_const*gravity*1e-5`**, not `0.1`. This port's `jmd95_eos` callers instead computed `pressure = -depth` (dbar) then let `jmd95_eos` do `p_bar = 0.1*pressure` — an implicit, hardcoded `0.1 bar/m`, independent of the model's actual `rho_const`/`gravity`.

**Quantitative confirmation** (not just qualitative plausibility, per the issue's own explicit ask): using `isomip`'s real capture, computed N² for two independent fully-wet columns (`x=1,y=50,t=11` and `x=10,y=60,t=6`, 0-indexed) both with the port's current `0.1 bar/m` pressure and with the corrected `rho_const*gravity*1e-5=0.101043 bar/m` (isomip's real `rhoConst=1030`/`gravity=9.81`), and compared both against MITgcm's own captured `sigma_r`-derived N² (`gravity*gravitySign*sigma_r/rho_const`). The current-code relative error reproduced the issue's own quoted evidence numbers essentially exactly (e.g. `3.30e-5`, `3.64e-5`, ... up to `1.02e-4` at the deepest level) — confirming the same mechanism and dataset — and the corrected-pressure relative error collapsed to floating-point noise (`~1e-16` to `~1.3e-11`) at every level tested, in both columns. This is a near-total elimination of the systematic component, not merely a directionally-consistent reduction.

**Fix**: added `main/eos.py::_depth_to_eos_pressure(depth, rho_const, gravity)` (returns `rho_const*gravity*1e-4*(-depth)`, the value `jmd95_eos` needs so its own internal `*0.1` reproduces MITgcm's real bar/m factor) and wired it into all three pressure-computing call sites: `compute_buoyancy_gradients`, `compute_ggl90_buoyancy_frequency_squared`, and `compute_static_instability_mask` (which needed a new `gravity` parameter threaded through — its single caller, `unified_driver.py::UnifiedColumnDriver._apply_convective_adjustment`, already had `self.gravity` available). `jmd95_eos` itself is unchanged (its own dbar→bar `*0.1` contract is untouched and correct as a *unit* conversion; the bug was purely in what its callers passed in as the pressure argument).

**Item 3 cross-check (why this was invisible until `isomip`) — checked honestly, does NOT hold as stated**: the issue asked whether every other captured experiment's `rho_const*gravity*1e-5` happens to be numerically close to `0.1`, which would explain the invisibility independent of the near-N²≈0 story.
