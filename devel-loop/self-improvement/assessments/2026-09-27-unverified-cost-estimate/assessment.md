# Assessment: an unverified quantitative figure entered an issue's own scoping text and nearly caused a wrong deferral

**Date**: 2026-09-27
**Owner issue**: TEAM-ESTIMATE-EVIDENCE-001
**Scope**: Arch's issue drafting, as exercised when 1DMIX-043 was split and
1DMIX-049 was filed.

## What happened

1DMIX-049 asked for the lost `global_oce_latlon` KPP capture to be regenerated by
a real Docker MITgcm rerun. Its filed text asserted the run was "8760 timesteps"
and would therefore cost hours of wall clock. That figure was wrong. It belongs
to `lab_sea` (1DMIX-026, hourly steps). `global_oce_latlon` uses 12-hour steps and
`nTimeSteps=720` — already the checked-in configuration, and directly confirmable
from the experiment's own `data` file (`externForcingCycle / deltaTtracer = 720`).

The figure came from grepping for a timestep count across the verification tree
and taking a match without confirming which experiment's record it belonged to.

## Correction and measured truth

Recorded in `closed_issues.md:1391`:

> Corrected a real error in this issue's own original text: the "8760 timesteps"
> figure actually belongs to a different experiment (`lab_sea`/1DMIX-026, hourly
> steps); `global_oce_latlon` uses 12-hour steps, and `nTimeSteps=720` ... is the
> correct full-run count -- 720x43,200s = 360 days = one full `externForcingCycle`.
> ... **the actual MITgcm run+parse for 720 timesteps is only ~15 minutes total,
> not the "hours" this issue's own text anticipated**

Measured directly: the full 720-timestep Docker run took 6m52s; reparsing the
resulting 13.82 GB `output.txt` took 6m57s. Total ~14 minutes, against a written
expectation of "hours".

Richard independently reconfirmed the reconciliation by reading both closed
issues himself and grepping the live `data` file, rather than accepting the
narrative.

## Potential consequence, had it not been caught

The issue had been *scoped* around the wrong number: its bounded first step
existed specifically to avoid committing to a supposedly multi-hour run. A
~15-minute task was one step away from being deferred as expensive. The
underlying work — this project's only genuinely multi-tile, realistic-forcing KPP
validation case — would have stayed lost for at least another iteration.

The general failure mode is worse than one wasted step: a wrong number in an
issue's own text is inherited by every later decision about that issue, including
prioritization and deferral, and it is not re-derived unless someone deliberately
challenges it.

## What actually caught it

Not review, and not a gate. It was caught because the issue's first bounded step
*measured a cheap prefix of the real command* (an 8-timestep smoke run with
timing) instead of reasoning about the estimate. The measurement disproved the
premise the issue had been written around.

## Quantified cost

One bounded first step (~15 minutes of dispatch) existed only because of the
wrong figure. The full run it was hedging against cost less than the hedge.

## Not measured

- Whether other filed issues in the root ledgers carry similar unverified

- Provider cost of the bounded first step (no reconciled accounting for this
  iteration — see `measured.cost_usd`, which is empty).
